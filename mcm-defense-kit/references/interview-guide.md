# 答辩访谈提纲

面向数学建模竞赛答辩的**结构化访谈指南**。目标：从用户嘴里问出那些"材料里读不到、但答辩一定会被问"的信息。

---

## 使用原则

1. **先材料，后访谈**。读完论文再问，问得更准。用户会觉得"你是真的懂我这篇"。
2. **一次最多 4 个问题**（AskUserQuestion 上限）。信息多就分轮次，别一口气塞 10 个问题把人问懵。
3. **不要评判**。用户可能不懂代码、论文是 AI 辅助写的。这些都是常态，你要做的是帮他把话圆回来，不是教育他。
4. **问不到就记下来**。答不上来的，在手册里写成「〔待补充：建议按 X 思路答〕」，不要自己编。

---

## 第一轮：基础信息（AskUserQuestion）

### Q1 · 赛制与答辩形式

> 这次是哪个比赛的答辩？什么形式？

选项：
- **国赛 · 线上**（腾讯会议共享屏幕，最常见）
- **美赛 · 线上**（英文，ZOOM）
- **研赛 / 其他**
- **线下答辩**（现场投影 + 评委席）

**为什么问**：决定 `01_答辩流程与准备.md` 里设备检查清单的内容。线上要查网络/麦克风/共享屏幕；线下要查投影分辨率/翻页笔/打印稿。

### Q2 · 时间分配

> 答辩总共多久？其中自述多久？

选项：
- **10 分钟自述 + 5 分钟提问**（国赛主流）
- **8 分钟自述 + 4 分钟提问**
- **15 分钟自述 + 10 分钟提问**
- **不确定 / 按通知**

**为什么问**：`02_自述讲稿.md` 严格按时长切段。10 分钟自述约 1400–1600 字，8 分钟约 1100–1300 字。结尾必须附一份「压缩版对照表」。

### Q3 · 手册深度

> 你希望这份手册写到什么程度？

选项：
- **能直接背**（完整版，每题给完整回答，约 5 万字）
- **够用就行**（精简版，只给要点和关键数字）
- **只要提纲**（自己现场组织语言）

**为什么问**：决定 B 类文档的详略。选"能直接背"就每题写满，选"只要提纲"就只写骨架。

### Q4 · 最大风险点

> 论文里有没有你自己都觉得"说不清"的地方？（可多选）

选项：
- **代码与论文不完全一致**
- **数据来源偏弱 / 是模拟的**
- **模型是现成方法改的，创新性不足**
- **用了 AI 辅助写作或建模**
- **没有明显短板**

**为什么问**：这是整份手册的**重点防御方向**。选了哪项，对应章节就要加倍写。

## 第二轮：材料追问（自由提问）

读完材料后，逐条核对。**答不上来的就当场问用户**。

### 主线与创新

| 要问出来的 | 追问话术 |
|---|---|
| 一句话创新 | "如果只能用一句话说你们这篇的创新，你会怎么说？" |
| 主线是否统一 | "问题一到问题四，用的是同一套框架还是四套不同的方法？" |
| 相比"标准做法"的差别 | "别人一般会怎么做？你们的做法差在哪？" |
| 最有把握的一问 | "四个问题里，哪一问你们最有信心？" |
| 最没把握的一问 | "哪一问你自己都觉得有点虚？" |

### 关键数字（**逐个核对，不能有错**）

- 全篇最优值是多少？在哪个问题？
- 数据规模：多少个样本 / 多少个约束 / 多少行代码？
- 迭代次数 / 运行时间 / 求解器用的是什么？
- 灵敏度分析里，参数变动多少百分比，结果波动多少？
- 改进幅度：相比初始方案，指标改善了多少？

> ⚠️ 数字必须**有出处**。论文里查不到就问用户，用户也不知道就标 `〔待确认〕`。**绝不编造**。

### 公式（每个主公式都问）

对论文里每一个**独立编号的公式**：

1. **是什么**：这个公式在算什么？
2. **为什么**：为什么用这个而不是别的？（这是评委最爱问的）
3. **怎么用**：在代码里对应哪段？参数怎么定的？
4. **注意什么**：有什么前提条件？什么情况下会失效？

如果用户答不出第 2 条，手册里就按"实用性优先"的角度组织答案（比如"因为它在我们的场景下更稳/更快/更容易解释"）。

### 代码

- 主程序入口是哪个文件？
- 跑一遍要多久？需要什么环境（Python 版本、依赖包）？
- 结果输出到哪里？
- 有没有写 README 或注释？

> 用户不懂代码也没关系 —— 问到什么记什么。`08_不懂代码的准备策略.md` 会专门处理这种情况。

### 局限与不足

**这一条一定要问，而且要认真问。**

> "如果评委问'你们这个模型有什么不足'，你们会怎么答？"

一般会得到三种反应：
- 能说出具体不足 → 直接写进手册，配上"我们是怎么缓解的"
- 说"没什么不足" → 危险信号，你要帮他找出 2–3 个（数据规模小 / 假设偏理想 / 只做了单目标 / 没考虑 XXX 因素）
- 完全答不上来 → 按通用方向写：数据覆盖度、假设适用边界、模型可扩展性

## 第三轮：分工确认（可选）

如果用户提到"三人分工"，问清楚：

- 谁是建模手 / 编程手 / 论文手？
- 各自负责哪几个问题？
- 谁的口才最好？（现场主答）
- 谁最了解代码？（技术追问时顶上）
- 谁负责看时间？

这些信息填进 `04_三人分工与准备清单.md`。

## 访谈后的整理

访谈结束，把答案整理成一份**内部笔记**（不交给用户），格式：

```yaml
赛制: 国赛线上，10分钟自述 + 5分钟提问
风格: 能直接背
风险: 代码与论文不一致；用了AI辅助

主线: 时间块展开 + 左闭右开区间重叠判定，四问共用一套判据
创新:
  - 模型统一（四问一套框架）
  - 冲突度指标（自创，可量化）
  - 优先级字典序（贴合实际业务）
数字:
  最大冲突度: 8
  最优解: 撤销 3 个 / 平移 7 个
  运行时间: 12 秒
不足:
  - 数据规模小，只验证了 100 个样本
  - 假设忽略传输时延

分工: 建模手A / 编程手B / 论文手C，C主答
```

这份笔记就是后面填 11 份模板的**唯一数据源**。

## 常见访谈失误

| 失误 | 后果 | 正确做法 |
|---|---|---|
| 只看论文不问人 | 手册里全是书面语，现场念出来很假 | 每题都问"你会怎么答"，按他的口吻组织 |
| 一次问 10 个问题 | 用户敷衍回答，信息质量低 | 分 2–3 轮，每轮 3–4 个 |
| 用户说"没有不足"就跳过 | 手册缺少最关键的防御章节 | 主动帮他找 2–3 个合理不足 |
| 编造数字补齐空白 | 现场被追问就崩 | 标 `〔待确认〕` |
| 不问时间分配 | 讲稿长度全错 | 必须问，或按 10+5 保守处理 |
